# Локальная серверная аналитика и production

Для бесплатного пилота Neon + Render подготовлена отдельная инструкция **[DEPLOY_RENDER_NEON.md](DEPLOY_RENDER_NEON.md)**. Публикация не выполнялась. Сервер переносим: Node.js 24, PostgreSQL, обычный HTTPS reverse proxy. Реальные исследовательские данные по умолчанию не собираются. Самостоятельный HTML всегда работает с аналитикой `off`.

## Запустить локально

Зависимости уже установлены. После переноса проекта: `npm.cmd ci --cache .npm-cache`.

В PowerShell из папки проекта:

```powershell
npm.cmd run build
$env:NODE_ENV = 'development'
$env:TELEMETRY_MODE = 'research'
$env:PUBLIC_ORIGIN = 'http://127.0.0.1:3000'
npm.cmd run admin:create
npm.cmd run server
```

`admin:create` спросит имя администратора и дважды пароль (минимум 16 символов), скрывая ввод. Создать пароль в менеджере паролей и сохранить там. CLI не печатает пароль; в базе сохраняется scrypt-хеш. Администратора создавать один раз. Для автоматизации доступны `--username` и `--password-file` с приватным локальным файлом; пароль аргументом командной строки не передаётся.

Книга: `http://127.0.0.1:3000/`. Панель: `http://127.0.0.1:3000/admin/analytics`. Поток для взрослых: `http://127.0.0.1:3000/research`. Отдельный Vite не требуется: сервер раздаёт production-сборку и API на одном origin.

Без `DATABASE_URL` в development используется **PGlite — настоящий PostgreSQL-движок**, который хранит данные в `runtime/dev-postgres/`. Это серверная база, не localStorage и не JSON-файл событий. Остановка/запуск Node сохраняет события и администраторов. Один сервер использует один каталог базы; не открывать его одновременно из CLI и работающего сервера. При добавлении администратора сначала остановить сервер.

Для внешнего PostgreSQL задать `DATABASE_URL`, например адрес своей локальной БД. Production обязательно требует внешний PostgreSQL; автоматического перехода на PGlite в production нет. HTTP допустим только для localhost; production требует HTTPS.

## Как проверить реальную запись

1. Войти в админку → «Configuración». Подтвердить, что согласие взрослого уже зарегистрировано исследователем, и получить одноразовый код. Код хранится в БД только как SHA-256-хеш и действует 7 дней.
2. В отдельном браузере/профиле открыть `/research`, прочитать информацию и активировать выданный код. Обычная детская кнопка не может самостоятельно дать исследовательский допуск.
3. Вернуться к книге, перелистнуть страницы и выбрать ветку. Через 10–15 секунд обновить панель. События появляются автоматически в БД и таблицах, импорт файла не нужен.
4. Отключить сеть в DevTools, выполнить действия, включить сеть: IndexedDB-очередь доставляется автоматически. Повторный event_id не создаёт вторую запись.
5. В настройках книги нажать «Dejar de participar». После подтверждения сервера новые события и старая очередь этого согласия не принимаются. Без сети интерфейс сообщает об ожидаемом подтверждении и хранит минимальный запрос отзыва отдельно от событий.
6. Перезапустить сервер: база и аналитика сохраняются. Локальная читательская книга продолжает работать без согласия.

Временные тесты **не являются согласием реальных участников**. До реального исследования владелец определяет цели, срок хранения, текст информации, способ проверки взрослого и порядок выдачи кодов. Галочка исследователя сама по себе не проверяет личность представителя.

## Режимы

`TELEMETRY_MODE=off` — нет аналитических событий. `debug` — ограниченная локальная история в памяти, без отправки и импорта в research. `research` — события разрешены только после серверной проверки согласия. Сохранение страницы книги живёт отдельно.

Конфигурация: `DATABASE_URL`, `PUBLIC_ORIGIN`, `HOST`, `PORT`, `NODE_ENV`, `RESEARCH_PROJECT_ID`, `TELEMETRY_MODE`, `TRUST_PROXY`, `DEV_DATABASE_PATH`. Пример без настоящих секретов: `.env.example`. Node-команды читают локальный `.env`, если он есть. Секреты нельзя помещать в Vite env или в bundle.

## API и защита

- Reader token и admin token — отдельные случайные HttpOnly/SameSite cookies; в production также Secure. База хранит их хеши. Reader token не открывает админку.
- Все admin API проверяют сессию, роль и project_id. Login, изменения и ingestion защищены CSRF-токеном и проверкой Origin. Login ограничен по частоте. Экспорт требует той же авторизации.
- Вход: `/api/admin/auth/login`; сессия: `/api/admin/auth/session`; выход: `/api/admin/auth/logout`. Предварительно получить CSRF через `/api/csrf`.
- Согласие: `/api/research/consents`; статус: `/api/research/status`; отзыв: `/api/research/consents/:id/withdraw`.
- События: `/api/telemetry/events`. Батч до 50 событий/64 KiB; строгое allowlist-поле payload. Transaction commit предшествует accepted_event_ids. IDs участника/согласия проверяются по допуску.
- Аналитика: `/api/admin/analytics/{summary,funnel,pages,audio,choices,tasks,sessions}`, `/sessions/:id`, `/export?format=csv|json&kind=raw|aggregates`.
- Настройки: GET/PATCH `/api/admin/research/settings`. Удаление: DELETE `/api/admin/research/participants/:id` с `{ "confirm": "DELETE" }`.
- Параметризованные SQL-запросы, FK и каскадное удаление. Экспорт не сохраняется в публичных файлах; CSV экранируется против формул. Минимальные audit-записи для экспорта/удаления/настроек не копируют события.

## Метрики

Идентификаторы участника, сессии, чтения, посещения страницы и проигрывания разделены. Сессия обновляется после 30 минут бездействия; новое явное перечитывание создаёт новое чтение. Время считается через `performance.now()`, отдельно для active/visible/audio. Heartbeat 15 секунд; скрытые/неактивные интервалы не добавляются к active. Это время использования интерфейса, не оценка внимания.

Воронка дедуплицируется по выбранной единице; знаменатель ветки — выбравшие её. Попытки matching/sequence считаются при `Comprobar`, свободные интерпретации имеют correctness=null. Audio starts не суммируются с repeats. Даты фильтра берутся по `received_at`, верхняя граница исключается; `client_ts` сохранено отдельно для восстановления хронологии. Одна и та же выборка применяется к карточкам, таблицам и экспорту. Максимум периода 366 дней/100000 событий; при большем объёме сузить период. Это явный предел первой версии, а не тихое усечение данных.

## Production на своём сервере

1. Установить Node.js 24 и PostgreSQL либо Docker/Compose. Не открывать порт БД наружу. Скопировать исходники без `.env`, runtime, backups и тестовых выгрузок.
2. Создать `.env` из примера, задать HTTPS `PUBLIC_ORIGIN`, пароль БД, `DATABASE_URL` и проект. Начать с `TELEMETRY_MODE=off`. Для Compose дополнительно `POSTGRES_PASSWORD` — длинный случайный URL-safe пароль, например hex. В приложенном Compose DATABASE_URL формируется внутри сервиса из этого пароля.
3. `docker compose up -d --build`. Используется постоянный PostgreSQL volume; миграции применяются повторяемо при запуске приложения. Либо `npm ci`, `npm run build`, `npm run db:migrate`, запуск Node под системным менеджером процессов.
4. `docker compose exec book node server/cli.mjs create-admin`. Первый пароль хранить в менеджере паролей. Это реальное создание администратора, не флаг localStorage.
5. Настроить HTTPS reverse proxy. Пример — `deployment/Caddyfile`; `BOOK_DOMAIN` указывает домен. Порт 3000 привязан к localhost. `TRUST_PROXY=1` допустим только за этим доверенным proxy; нельзя открывать Node напрямую в интернет с таким доверием.
6. Проверить вход и прямые API-запросы без cookie (401), HTTPS и Secure cookies, доступность БД после перезапуска, экспорт/удаление/backup restore. После согласования исследования включить research и перезапустить приложение.

Docker/Compose и публичный HTTPS здесь **не развёрнуты и не проверены**. 3 ноября 2026 адаптер `pg` дополнительно проверен на отдельном локальном PostgreSQL 18.6 по TLS, включая миграции, consent/events/CSV/withdraw/delete и перезапуск Node. Neon проверяется отдельно с локальным секретным файлом; подробности в отчёте подготовки.

Production проверяет TLS-сертификат и имя хоста PostgreSQL (`sslmode=verify-full`); `require` приводится к `verify-full`, небезопасные режимы отклоняются. Для старого Compose теперь также нужны сертификаты: перед запуском на Linux подготовить `backups/postgres-tls/server.crt` и `server.key`, сертификат с SAN `DNS:postgres`; приватный ключ должен принадлежать postgres внутри контейнера и иметь права 0600. Пример создания для изолированного сервера: `openssl req -x509 -newkey rsa:3072 -nodes -days 365 -keyout backups/postgres-tls/server.key -out backups/postgres-tls/server.crt -subj /CN=postgres -addext subjectAltName=DNS:postgres`. UID/GID брать из выбранного образа postgres, права устанавливать на хосте перед запуском. Это отдельный Docker-вариант, для Neon/Render он не используется и не тестировался.

## Retention и backup

Default хранения — технические 90 дней, меняется в админке, не правовая рекомендация. Сервер раз в 24 часа удаляет старые события и неактивные сессии; одноразовый запуск — `node server/cli.mjs retention` (для PGlite предварительно остановить основной сервер). Истёкшие токены/коды также удаляются. Живые агрегатные кеши и временные экспортные файлы не создаются. Tombstone согласия препятствует восстановлению его старой очереди; без соответствующего допуска ingestion в любом случае отклоняется.

Для PostgreSQL/Compose выполнять backup **внутри контейнера**, чтобы PowerShell 5 не испортил бинарный поток:

```text
docker compose exec postgres pg_dump -U book -d tomas -Fc -f /backups/tomas.dump
docker compose exec postgres pg_restore -U book -d tomas --clean --if-exists /backups/tomas.dump
docker compose exec book node server/cli.mjs retention
```

Restore выполнять в изолированной базе/в период остановки приложения. Каталог `backups/production` защитить правами доступа и шифрованием диска; срок истечения резервных копий определить вместе с исследовательской retention-политикой. Перед повторным открытием после restore применить список удалений/отозванных согласий и retention, иначе старый backup может вернуть удалённые записи. Локальный PGlite можно копировать как каталог только после корректной остановки сервера.

HTTP получает IP технически; приложение не помещает его в события или журналы. Rate limiter держит служебные адреса в оперативной памяти на ограниченное окно. Proxy/host access logs настроить отдельно: минимизация, доступ, срок удаления; не логировать тела, токены и cookies.

## Автоматическая проверка

```powershell
npm.cmd run check
npm.cmd run test:server
npm.cmd run test:research
npm.cmd run test:telemetry
```

`test:research` поднимает временный локальный сервер на 3015 с отдельной PostgreSQL-базой, создаёт временного администратора и код, проходит взрослый поток, автоматически записывает действия, проверяет две вкладки, offline/retry, панель, CSV, отзыв и сохранность БД после перезапуска. Настоящих участников и согласий он не создаёт. `test:layout`, `test:browser` и `test:telemetry` запускаются при работающем Vite. Для браузера можно задать `BOOK_BROWSER_PATH`; на других платформах используется стандартный установленный Playwright Chromium.
