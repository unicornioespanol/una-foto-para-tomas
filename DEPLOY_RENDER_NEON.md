# Подготовка пилота Neon + Render

Подготовлено 3 ноября 2026 по `codex_deploy.md`. **Ничего не опубликовано**, GitHub-репозиторий не создан, Render не подключён. Созданную владельцем Neon не изменяли. Сюжет, задания, изображения и MP3 сохранены. Итог проверок: [DEPLOY_PREP_REPORT.md](DEPLOY_PREP_REPORT.md).

## Схема и стоимость

Один Render **Free Web Service**, runtime **Node**, обслуживает `dist/`, API, `/research` и страницу входа `/admin/analytics`. Постоянные события, пользователи и сессии находятся в Neon PostgreSQL через существующий `pg`. PGlite используется только для разработки, production без `DATABASE_URL` останавливается. HTTPS выдаёт Render; cookies в production Secure/HttpOnly/SameSite=Strict.

Стоимость выбранных Free-тарифов — **$0 / 0 ₽ в пределах бесплатных лимитов**, собственный домен не нужен. Не добавлять платные экземпляры, Render Postgres или платёжный метод ради этого пилота. Состояние тарифов сверено с [Render Free](https://render.com/docs/free) и [Neon Pricing](https://neon.com/pricing). Render: 750 часов на workspace в месяц, сон через 15 минут, пробуждение около минуты; локальные изменения файлов теряются. Без платёжного метода превышение включённых квот может остановить сервис/новые сборки. Neon Free заявляет отсутствие временного срока и требования карты; фактические квоты смотреть в своём кабинете. Доступность регистрации и проверки аккаунта у конкретного владельца не подтверждена. Это технический пилот.

## 1. Локальная проверка Neon — без публикации

База уже создана. Для автоматического теста использовать **отдельную тестовую ветку/базу**, без настоящих участников. В Neon Connect выбрать прямое подключение для администрирования/backup; pooled URL допустим для приложения. Не отправлять строку подключения в чат и не помещать её в команды, отчёты или GitHub.

Локально в редакторе создать `.env.neon.local` (игнорируется Git и Docker):

```dotenv
NODE_ENV=production
DATABASE_URL=postgresql://USER:SECRET@YOUR-HOST.neon.tech/neondb?sslmode=verify-full&channel_binding=require
RESEARCH_PROJECT_ID=tomas
```

Подставить URL только в локальном файле, сохранив query-параметры Neon. В PowerShell из папки книги:

```powershell
node --env-file=.env.neon.local server/cli.mjs check
npm.cmd run test:postgres
```

Первый вызов проверяет соединение без миграций, не печатает URL. Тест использует **новую случайную схему** в указанной базе, проверяет миграции дважды, весь серверный набор, отдельный процесс Node на localhost:3027, создание тестового администратора, consent → events → перезапуск → CSV → withdraw/delete. В конце удаляет только свою тестовую схему. Никаких настоящих согласий этот тест не создаёт. Если порт занят, задать локально `POSTGRES_TEST_PORT`. Тестовую ветку Neon после проверки можно удалить в кабинете; основной проект не удалять.

TLS в production обязателен, с проверкой имени сервера; отказ при недоверенном сертификате не обходить `rejectUnauthorized:false` или `NODE_TLS_REJECT_UNAUTHORIZED=0`. [Neon рекомендует verify-full](https://neon.com/docs/connect/connect-securely). В `pg` также включён `enableChannelBinding`; параметр libpq `channel_binding` сам по себе не заменяет настройку Node-драйвера.

## 2. Миграции и первый настоящий администратор

Создать отдельный `.env.production.local` с URL **целевой** базы (не тестовой ветки), `NODE_ENV=production`, `RESEARCH_PROJECT_ID=tomas`. При создании/миграциях сайт ещё не нужен:

```powershell
node --env-file=.env.production.local server/cli.mjs check
node --env-file=.env.production.local server/cli.mjs migrate
node --env-file=.env.production.local server/cli.mjs migrate
node --env-file=.env.production.local server/cli.mjs create-admin
```

Ввести имя и дважды пароль из менеджера паролей, не короче 16 символов. Пароль скрыт и не выводится. При повторе того же имени CLI завершится ошибкой, пароль существующего пользователя не заменяется. Публичного setup API нет. Не запускать эту команду в build/start Render.

Для контролируемой автоматизации: `create-admin --username owner --password-file backups/admin-password.txt`, где файл содержит одну строку и доступен только владельцу. На Windows права POSIX 0600 не заменяют ACL: проверить NTFS-доступ. После создания удалить временный файл через редактор/проводник. Пароль хранить в менеджере паролей. Секрет подписания сессии не требуется: текущая архитектура использует случайные непрозрачные токены и хеши в PostgreSQL.

Миграции транзакционные, повторяемые, с transaction-scoped advisory lock для `pg`; совместимы с пулом Neon. При старте сервер также применяет их и retention, затем запускает обычный суточный таймер retention.

## 3. Подготовить GitHub

В текущей папке Git-репозиторий отсутствует. **Обычная загрузка папки через веб GitHub не учитывает `.gitignore`**: не перетаскивать весь каталог. Использовать Git/GitHub Desktop и проверить staged-файлы до commit/push. Не добавлять `.env*` (кроме `.env.example`), `runtime/`, `backups/`, `test-results/`, SQL-дампы, ключи/сертификаты, `node_modules/`, `.npm-cache/`, `dist/`, `offline/`, сгенерированный HTML. Исходники, `assets/` с MP3, `data/`, `server/`, `src/`, `tools/`, package/lock и конфигурация нужны для сборки. `book_update/` — исходный пакет графики, сервер его не обслуживает; можно оставить локально.

Для локального Git перед коммитом:

```powershell
git init
git add .
git diff --cached --name-only
git status --short
git check-ignore .env.neon.local .env.production.local backups/pg-deploy-proof.dump
```

Проверить staged-содержимое в GitHub Desktop/редакторе. Создание репозитория и push выполнять только после отдельного решения владельца; сейчас они не выполнялись.

## 4. Render — только после разрешения на публикацию

Само создание Web Service/Blueprint может запустить **первую** публикацию. Отключение auto deploy запрещает последующие автоматические публикации, но не заменяет разрешение на первый запуск. Сейчас этот шаг **не выполнять**.

После решения владельца: New → Web Service → GitHub → нужный репозиторий → **Node**, **Free**, регион Frankfurt (либо ближайший к выбранной Neon). Не выбирать Docker только потому, что в репозитории есть Dockerfile. Корень проекта — корень репозитория.

| Настройка | Значение |
|---|---|
| Node | 24.x, задано в package.json |
| Build | `npm ci --include=dev && npm run build` |
| Start | `npm run server` |
| Health Check | `/healthz` |
| Auto Deploy | Off |

`--include=dev` нужен для Vite/sharp при `NODE_ENV=production`. Скрипт сборки создаёт `dist/`, отдельные MP3 и локальную offline-копию. Render обслуживает только `dist/`. Shell/SSH/one-off jobs на Free не используются. Подготовленный `render.yaml` повторяет эти настройки и **не** создаёт БД/платный ресурс. [Команды собственного Express-приложения задаются в Render](https://render.com/docs/deploy-node-express-app).

В Render Environment вручную сохранить:

| Переменная | Значение |
|---|---|
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` |
| `PORT` | Выдаёт Render; вручную не фиксировать |
| `PUBLIC_ORIGIN` | Точный `https://ИМЯ.onrender.com` без завершающего `/`, пути и query |
| `DATABASE_URL` | Секретный URL целевой Neon, TLS verify-full |
| `RESEARCH_PROJECT_ID` | `tomas` |
| `TELEMETRY_MODE` | **`off`** |
| `TRUST_PROXY` | `1` — только за reverse proxy Render |

Не использовать `VITE_DATABASE_URL` или другую `VITE_` переменную для секрета. В обычном браузере `/api/config` должен вернуть `mode: off`. Ни события, ни регистрация нового согласия при этом не принимаются. Читательское сохранение книги работает независимо от серверной аналитики.

## 5. Проверка после будущего выпуска

1. Проверить HTTPS, `/healthz` → 200, `/api/config` → off. Прямые document-маршруты SPA открывают HTML, неизвестный `/api/...` → JSON 404, отсутствующий MP3 → 404. Ответ API не подменяется страницей книги.
2. Пройти photo/song, photo/story, drawing/song, drawing/story; проверить Escuchar, Pausa, Continuar, Repetir, уход со страницы и короткие реплики на компьютере и настоящем телефоне.
3. В приватном окне API `/api/admin/analytics/summary` и `/api/admin/analytics/export?format=csv` → 401. `/admin/analytics` показывает форму входа: её HTML публичен, данные доступны только после серверной авторизации. После входа проверить CSV/JSON; неверный Origin/CSRF → 403.
4. Для research-потока сначала выполнить локальный `test:postgres` на отдельной тестовой базе. Для проверки публичного HTTPS создать отдельно согласованный технический стенд с тестовой Neon и временным `TELEMETRY_MODE=research` либо согласовать короткое тестовое окно. На основной ссылке off не менять без отдельного решения. Использовать только синтетического/взрослого тестового участника и действительный одноразовый код; проверить consent → чтение → события → CSV → перезапуск сервиса → те же данные → отзыв → запрет старой очереди → удаление → отсутствие событий.
5. Проверить backup/restore ниже. Только после этих проверок пометить публичный пилот принятым. Эта подготовка сама по себе не подтверждает публичный HTTPS или подключение к вашей Neon.

## 6. Резервная копия и восстановление

CSV/JSON из админки — экспорт событий, **не полная резервная копия**. Для восстановления нужны также схема, согласия, tombstones, хеши учётных записей и сессий. Установить PostgreSQL client tools версии не старше сервера Neon (pg_dump/pg_restore) и GnuPG для шифрования. Указать каталог client tools локально в `PG_BIN_DIR`, если они отсутствуют в PATH. Не включать эти инструменты в frontend или репозиторий.

`tools/pg-tool.mjs` передаёт пароль дочернему процессу через окружение, не аргументы, использует verified TLS и не печатает диагностику с URL. На Linux доверенные roots обычно находятся автоматически; Windows/libpq может потребовать путь к доверенному CA в `PGSSLROOTCERT` либо `sslrootcert` в локальном URL — см. [документацию Neon по TLS](https://neon.com/docs/connect/connect-securely). Ошибку доверия не обходить отключением TLS-проверок.

На время полного backup остановить согласованные исследовательские изменения:

```powershell
node --env-file=.env.production.local tools/pg-tool.mjs dump backups/book-2026-11-03.dump
gpg --symmetric --cipher-algo AES256 --output backups/book-2026-11-03.dump.gpg backups/book-2026-11-03.dump
```

GnuPG запросит отдельную парольную фразу; сохранить её в менеджере паролей отдельно от зашифрованного файла. Не писать фразу в команду. Каталог backups не публикуется; хранить на защищённом диске. Для проверки использовать **новую пустую** тестовую БД Neon и `.env.restore.local` с её URL:

```powershell
gpg --output backups/restore-check.dump --decrypt backups/book-2026-11-03.dump.gpg
node --env-file=.env.restore.local tools/pg-tool.mjs restore backups/restore-check.dump
node --env-file=.env.restore.local server/cli.mjs check
```

Wrapper откажется восстанавливать в БД с пользовательскими таблицами, `--clean` не применяется. Проверить вход и число тестовых событий/согласий в восстановленной БД на изолированном стенде. Зафиксировать дату проверки; удалить незашифрованные временные dump-файлы после успешной проверки, оставив шифрованную копию и отдельную фразу. На SSD удаление файла не гарантирует физическое стирание: для исходных дампов использовать зашифрованный диск.

Перед возвратом восстановленной БД к работе применить актуальные удаления/отозванные согласия и retention: `node --env-file=.env.restore.local server/cli.mjs retention`. Срок жизни резервных копий согласовать со сроком хранения; старые копии могут вернуть ранее удалённые записи. GnuPG и восстановление именно вашей Neon здесь пока не проверялись.

## Что остаётся у владельца

Проверить реальный регион Neon и использование Free без платёжных данных; сохранить секретные файлы локально; провести доступную проверку подключения; создать настоящего администратора; после отдельного разрешения загрузить проверенные исходники в GitHub и создать Render Free. Проверить на телефоне и сохранить зашифрованный backup. Реальные детские данные и публичную подробную телеметрию до отдельного решения не включать. Условия использования записей и необходимое авторство аудио проверить перед публикацией; источник лицензии в проекте не установлен, приписывать ElevenLabs без подтверждения не стали.
